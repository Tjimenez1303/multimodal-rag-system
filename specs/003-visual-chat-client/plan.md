# Implementation Plan: Visual Chat Client

**Branch**: `feature/visual-chat-client` | **Date**: 2026-09-29 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/003-visual-chat-client/spec.md`

## Summary

A technician opens <http://localhost:3000>, asks questions about the ingested manuals,
and reads each answer with its sources and the figure it depends on beside it. The
technician can also upload manuals and follow their processing from a side panel. The
client is a static React application served by nginx, which also proxies the API on the
same origin. It adds no answering logic and displays the service's responses as
returned.

- **Conversation.**
  - One reducer holds the turns, stored in `sessionStorage` so they survive a reload of
    the tab and disappear with it.
  - A queue sends one question at a time, holds questions submitted meanwhile, and
    aborts the open request when the user presses stop. nginx forwards the abort to the
    API, which cancels the question.
- **Answers.**
  - AI Elements' `MessageResponse` (Streamdown) renders the answer in static mode. Raw
    HTML is shown as text, Markdown images are never loaded, and `[n]` markers become
    links to their numbered source lines.
  - Each turn is a two-column grid: the text and the source lines on the left, the
    primary figure and the related figures on the right.
  - Figures and pages open in shadcn/ui modal dialogs.
- **Interface.** The screen is composed from shadcn/ui and Vercel AI Elements components
  installed with their CLIs. The feature's own components hold only its logic.
- **Failures.** Every service error code maps to a plain-English message and a retry
  action. Each request carries an `X-Request-ID` created in the browser, shown as
  "Reference: …" so the failure can be found in the API logs.
- **Documents.** A collapsible panel uploads with transfer progress, lists the library
  and polls unfinished documents every 2 seconds. It also holds the selection that
  restricts questions.
- **Page images.** The worker keeps the page renders Docling already produces during
  extraction and stores them as PNG. A new route,
  `GET /api/v1/documents/{document_id}/pages/{page_number}/image`, serves them, so no PDF
  is processed inside a request. A ready document also opens in the same page view from
  the panel, stepping through all its pages.
- **Deletion.** `DELETE /api/v1/documents/{document_id}` removes a document that is not
  being processed: its index points first, then its stored files, then its database
  rows. The panel offers it on ready and failed documents behind a confirmation. With
  the page images, these are the feature's only backend changes.
- **Delivery.** A `frontend` service joins `compose.yaml`, so `docker compose up` starts
  the whole system. This closes the Principle IX deviation carried by features 001 and
  002.

Decisions, alternatives and measurements are in [research.md](research.md).

## Technical Context

**Language/Version**:

- TypeScript `~6.0` in strict mode, on Node 24 LTS (pinned in `frontend/.node-version`),
  managed with npm and a committed `package-lock.json`.
- Python 3.14 with uv for the backend change.

**Primary Dependencies**:

- **Frontend runtime**:
  - React 19.3
  - TanStack Query 5.104
  - shadcn/ui components (CLI 4.21) on Radix primitives (`radix-ui` 1.6), styled with
    Tailwind CSS 4.3 through `@tailwindcss/vite`, with `lucide-react` icons
  - Vercel AI Elements 1.9 components (Conversation, Message, MessageResponse,
    PromptInput, InlineCitation, Sources), which bring Streamdown 2.6 and
    `use-stick-to-bottom` 1.1
  - `mdast-util-find-and-replace` 3.0 and `unist-util-visit` 5.0 for the answer's remark
    plugins
  - zod 4.6, used by the generated client to validate response bodies
  - The typed fetch client generated by `@hey-api/openapi-ts` 0.99
- **Frontend build and tests**:
  - Vite 8.3 and `@vitejs/plugin-react` 6.1
  - oxlint 1.86 and Prettier 3.9
  - Vitest 5.0 with `@vitest/coverage-v8`, jsdom 30, React Testing Library 16,
    `user-event` 14 and MSW 3
  - Playwright 1.63 and `@axe-core/playwright` 4.13
- **Serving**: `nginx:1.30-alpine` (stable line), with its built-in `envsubst`
  templates.
- **Backend**: no new dependency. Docling's `generate_page_images` option and the
  existing blob storage are reused.

**Storage**:

- **Browser**: `sessionStorage` for the conversation, the selection and the panel state
  (data-model section 1).
- **Blob volume**: page images under `pages/{document_id}/{page}.png`, about 0.45 MB per
  page (research section 12).
- No database change.

**Testing**:

- **Unit and component**: Vitest and React Testing Library, with MSW network fakes
  serving contract-shaped fixtures and a 90% line coverage gate.
- **Reference answer set**: at least 20 responses in `frontend/tests/fixtures/answers/`.
- **End to end**: Playwright in Chromium, Firefox and WebKit, with the API faked by route
  handlers, plus axe accessibility checks.
- **Backend**: pytest for the new use case, the route and the extractor change, with
  contract tests that include the 003 contract. The 90% gate stays.

**Target Platform**:

- Current desktop Chrome, Firefox, Safari and Edge, in windows of 1280 × 720 or larger.
- Linux containers through Docker Compose. The reference machine is the Apple M4 Pro of
  features 001 and 002.

**Project Type**: web application, with a new `frontend/` single-page client next to
the existing `backend/` service.

**Performance Goals**:

| Criterion | Target | Basis |
|---|---|---|
| SC-006 | Working indicator within 0.5 s | Rendered synchronously when the turn is added, before the request starts |
| SC-009 | 95% of status changes shown within 5 s | 2 s polling of unfinished documents only |
| SC-010 | 50 turns with images stay responsive | Memoized `MessageResponse` per turn, lazy images, no re-render of old turns while typing |
| SC-011 | Page view within 3 s | Stored PNG of about 0.45 MB served from the local volume, no rendering on request |
| SC-012 | Client reachable after startup | `frontend` healthcheck, `depends_on: api` healthy |

**Constraints**:

- The client contacts only its own origin (FR-046). This is enforced by a
  `Content-Security-Policy` of `'self'`, and no fonts, CDNs or analytics are used.
- Answer content is displayed, never executed (FR-009).
- The conversation never leaves the browser (FR-003).
- The client wait limit, 105 s by default, stays above the service's 90 s deadline.
  Every other browser call times out after 10 s.
- Uploads fail after 60 s without transfer progress.
- The page image route reads stored files only. PDF processing stays in the worker
  (Principle III).

**Scale/Scope**:

- One organization, no authentication, one conversation per tab.
- Libraries of at least 100 manuals, listed 50 at a time.
- About 4.5 GB of page images for 100 manuals of 100 pages.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | How this plan complies | Status |
|---|---|---|
| I. Hexagonal architecture | Backend: `GetPageImage` and `DeleteDocument` live in `ingestion/use_cases/library.py` and uses only ports. The route only translates HTTP. Frontend: the service is reached only through `src/client/` (generated) and `src/api/` (request id, problem parsing, upload), and components never call `fetch` directly | Pass |
| II. Ports and adapters | No new backend port. `DocumentExtractor` gains page images through `ExtractionBatch`, which the Docling adapter and the fake extractor both fill. `DocumentRepository` gains `delete` and `BlobStorage` gains `delete_tree`, each implemented by its adapter and its fake. Wiring stays in `bootstrap.py` | Pass |
| III. Asynchronous ingestion | Page images are produced by the worker during extraction, under stable keys that a retried job overwrites. The API only reads stored files, and no PDF is opened in a request. Deletion removes stored files and rows without opening a PDF, and is refused while a job is pending or processing | Pass |
| IV. Multimodal fidelity | Page images keep the 1-based page numbering of every element. Figure positions and captions are displayed as stored | Pass |
| V. Grounded answers | The client keeps the history (tab `sessionStorage`), renders Markdown, and shows citations as document and page with the related image next to the answer. It adds no answering logic (FR-022) | Pass |
| VI. Resilience | Every browser call has a timeout. Questions: an abortable wait limit above the service deadline. Configuration, library and status calls: a 10 s timeout and TanStack Query retries with backoff. Uploads: a 60 s stall timeout. Service errors are mapped by code in one table ([contracts/client.md](contracts/client.md)). Backend: the new `PageNotFoundError` is a `NotFoundError`, the new `IngestionInProgressError` is a `ConcurrencyError`, a missing blob is a `DataInconsistencyError`, and all go through the existing single mapping. Every deletion step tolerates what is already gone, so an interrupted deletion is retried by asking again | Pass |
| VII. Observability | The browser-generated `X-Request-ID` reaches the API logs and is shown as the failure reference. nginx writes JSON access logs with the time, method, path without query string, status, duration and `X-Request-ID`, and never the client address. The client sends no telemetry. Backend page image requests get the existing per-request log line | Pass |
| VIII. Test discipline | Frontend: MSW and route fakes over contract fixtures, no module mocks, citation and image rendering tests, a 90% gate. Backend: fakes, contract tests and the 90% gate | Pass |
| IX. Configuration and delivery | `docker compose up` now starts the frontend with a healthcheck. Runtime values come from environment variables rendered into `/config.json`, and `.env.example` documents them | Pass (closes the deviation of features 001 and 002) |
| Engineering standards | uv, ruff and mypy for the backend change. Frontend: TypeScript strict, oxlint (the official Vite scaffold's linter) and Prettier (react.dev's recommendation), all in pre-commit and CI. Code is grouped by concern (`conversation/`, `answer/`, `images/`, `documents/`, `failures/`) | Pass |
| Documentation standards | Google-style docstrings in Python and TSDoc on exported TypeScript functions and components. ADR 0006 (chat client stack and serving) and ADR 0007 (page images at ingestion). README: architecture diagram with the frontend (draw.io), getting started at port 3000, frontend development and tests. AGENTS.md commands gain the frontend rows | Pass |
| Development workflow | Spec Kit flow, `feature/visual-chat-client` branch, Conventional Commits, squash merge. Node tooling is pinned, the CI actions added are pinned by SHA, and zizmor audits them | Pass |

**Post-design re-check (after Phase 1)**: all gates still pass. The design adds one
backend route and one extractor option, both inside existing ports. The frontend reaches
the service through one module and keeps no answering logic. There is no deviation to
record in Complexity Tracking. The later addition of document viewing and deletion
(research section 18) adds one route and two port members and keeps every gate.

**Structure Decision**: the web application layout. `frontend/` is a new top-level
project with its own toolchain and image, next to `backend/`. Inside it, code is grouped
by concern: conversation, answer, images, documents and failures. The service is reached
only through `api/` and the generated `client/`. The backend change stays inside the
existing ingestion core, adapters and composition root, with no new package.

## Complexity Tracking

No constitution deviation. The notable choices, each explained in research.md, are:

- Page images rendered at ingestion instead of on request (section 12), at about 0.45 MB
  per page of storage.
- A runtime `/config.json` rendered by nginx instead of build-time Vite variables
  (section 11).
- An `XMLHttpRequest` upload next to `fetch` everywhere else, for transfer progress
  (section 7).
